## Unverified / blocked

**226M messages / 7.8M msg/s / 29.0s end-to-end throughput** (`README.md`) — blocked on a raw
ITCH `.bin`/`.NASDAQ_ITCH50` file, not present locally (`data/` has only derived CSVs).
Unaffected by the benchmark-harness fix (it's an aggregate wall-clock measurement, never
per-op timed). To re-verify when a file is available:

```bash
./lob_engine <file.NASDAQ_ITCH50> <TICKER> <output.csv>
# then update the figure and its "pending re-verification" label in README.md and bench/BASELINE.md
```

**All `data/features_*.csv` and `data/panel_*.csv` are stale and need regeneration** — same
raw-ITCH-file blocker as above. `data/features_AAPL.csv` (mtime 2026-05-04) and
`data/panel_AAPL.csv` (mtime 2026-06-13) predate commit `257956e` (2026-07-23), which fixed a
4-byte read misalignment in the ITCH stock-symbol field. Every derived CSV/panel file was
generated by the pre-fix parser and has a corrupted reconstructed book (verified via
`quoted_spread` — 99.6–100% of rows show `uint32_t`-underflowed spreads in the hundreds of
thousands of dollars, across all 5 tickers checked). Today's engine code is confirmed correct
(clean synthetic repro produces sane spreads). To regenerate once a raw file is available:

```bash
./lob_engine <file.NASDAQ_ITCH50> <TICKER> data/features_<TICKER>.csv
# repeat per ticker/day to rebuild the panel_*.csv files, then rerun results/OFI_STUDY.md's
# methodology (day-level split, HAC(5)) against the fresh data — the methodology itself
# does not need to change, only the input data.
```

## Open items (not investigated further — flagged, not resolved)

- **ASan/UBSan build hang.** Reproduces on pre-item-3 code too, so not caused by the
  pool-allocator fix. Hypothesis (unconfirmed): macOS ASan environment pathology. Logged in
  `audit/FINDINGS.md`; not investigated per explicit instruction to log-only.
- **Tail percentiles (p99, p999) are not reliably measurable without core pinning** on this
  unpinned, multi-tenant host. Documented in `bench/BASELINE.md` and `README.md`.
- **p99 cv spread across benchmarks has no established mechanism.** ReplaceOrder cv=1.64% vs
  DeleteOrder cv=96.93%, with no clean relationship to op cost, op type, or anything else
  checked so far. Recorded as an observation only — no mechanism should be assumed or cited
  until it's actually tested.
- ~~AMZN's contemporaneous OFI→return R² unexplained~~ — **resolved 2026-07-24**: root cause
  found (stale pre-item-4-fix data, corrupted book reconstruction, affects all 5 tickers, not
  AMZN-specific). See `results/OFI_STUDY.md` "Blocker 1". Superseded by the broader "all
  research data is stale" finding in Unverified/Blocked above.
- **The engine's single-ticker parsing architecture relies on `order_ref` global uniqueness
  across tickers, unverified against real data.** `'D'`/`'U'`/`'E'`/`'C'`/`'X'` ITCH messages
  are not filtered by ticker at all (no `stock_locate` resolution exists in this codebase —
  filtering happens only on `'A'`/`'F'` via the embedded symbol string). Safe for real ITCH
  data per Nasdaq's uniqueness guarantee, but this has never been exercised against a real
  multi-ticker file locally. Worth a defensive test once a raw ITCH file is available.
