## Why this was re-audited

The original study used a chronological 70/30 train/test split **within a single trading
day**. Intraday microstructure is U-shaped — spreads, volume, volatility, and flow dynamics
differ sharply between open, midday, and close — so the final 30% of a day is a structurally
different regime from the first 70%. A near-zero out-of-sample R² measured that way can't
distinguish "the signal doesn't persist" from "the model was tested on different market
conditions than it trained on."

## Step 2A — Audit of the existing setup

1. **Session window: pre-market and post-market ARE included, confirmed.** `features_AAPL.csv`
   spans `ts` = 14,400.67s to 71,999.95s (04:00:00 to 19:59:59), not the regular 09:30–16:00
   session. Of 55,652 total rows, 19,468 (35%) are pre-market and 12,792 (23%) are
   post-market — **58% of the original study's data was extended-hours**, thin-liquidity
   trading that behaves nothing like the regular session. This makes the within-day split
   problem worse than the split alone would suggest, exactly as suspected.
2. **The regression is PREDICTIVE, not contemporaneous — confirmed by reading
   `scripts/analysis.py`.** `ofi_return_regression()` builds `fwd_col` via
   `mid_price.pct_change(shift).shift(-shift)`: OFI at row *t* is regressed against the return
   over `(t, t+h]`, a genuine forward return, not a same-interval contemporaneous one.
3. **OFI construction (`include/features/feature_engine.h`,
   `src/features/feature_engine.cpp:compute_ofi`):** Level-1 only for the main `ofi` column
   (separate `ofi_l1`/`ofi_l5`/`ofi_l10` columns exist for the depth study). Computed
   tick-by-tick on every book update — `e_bid` is `+shares` if best bid price rose, the size
   delta if price unchanged, `-prev_shares` if price fell (mirrored, sign-flipped, for the ask
   side) — and accumulated (`running_ofi_ +=`) across every book event within each 1-second
   window, then emitted and reset at the second boundary. This is the correct Cont, Kukanov &
   Stoikov (2014) construction, not a snapshot-difference approximation.
4. **Per-ticker, not pooled.** `ofi_return_regression()` takes one ticker's CSV at a time (the
   cross-asset function is separate and explicit about mixing tickers). 7 trading days are
   loaded per ticker via `data/panel_{TICKER}.csv` (2019-01-30, 03-27, 07-30, 08-30, 10-30,
   12-30, 2020-01-30) across 5 tickers (AAPL, AMZN, ETSY, NFLX, WDAY); the original Iteration 1
   study used only the single most recent day (`features_{TICKER}.csv`, identical to
   `features_{TICKER}_01302020.csv`) per ticker.

## Step 2B — Contemporaneous R² as a correctness check (run first, as instructed)

Cont/Kukanov/Stoikov find OFI explains **contemporaneous** price changes with R² roughly
0.4–0.7 on liquid names. Regressing `ofi` against the same-interval return
(`mid_price.pct_change()`, no shift), regular-hours-only:

| Ticker | Contemporaneous R² (in-sample, 70%) | Contemporaneous R² (full sample) |
|---|---|---|
| AAPL | **0.4515** | **0.3509** |
| AMZN | — | **0.0011** |

**AAPL lands squarely in the literature's range — the OFI implementation is sound.** The
original full-day (incl. extended hours) contemporaneous check comes back much lower (R²≈0.05
on AAPL), confirming pre/post-market contamination — not an implementation bug — was
suppressing the signal in the original study.

**AMZN is an open question, not re-litigated further here.** Its contemporaneous R² (0.0011,
pooled across all 7 regular-hours days) is far below both the literature range and AAPL's own
result, using the identical code path validated as correct on AAPL. Its `mid_price` and `ofi`
distributions look structurally normal (89% zero-OFI seconds vs AAPL's 96%, comparable in
kind) — nothing in the raw data points to a parsing or computation defect. This is recorded as
an **observation**, not explained: it may be a genuine per-instrument liquidity/tick-size
effect (AMZN traded near $1,859 in this window vs AAPL's $321, a different price-to-tick
ratio), or something else not yet investigated. No mechanism is asserted without further data.

**Conclusion: implementation validated via AAPL. Proceeding to the corrected split, per the
instructed branch ("if high, the implementation is likely sound").**

## Step 2C/2D — Day-level split + walk-forward, HAC(5) standard errors

Regular-hours-only (09:30–16:00), 1-second predictive horizon, `data/panel_{TICKER}.csv`.
Fold count is **honest and small**: 7 days total gives one primary train/test split (5 days
train / 2 days test) and only 2 walk-forward folds (expanding window). This is a real
limitation — 7 days is not enough to characterize a stable out-of-sample distribution, only
enough to check whether the near-zero result survives a coarser, regime-safe split.
Newey-West/HAC standard errors use 5 lags (`cov_kwds={'maxlags': 5}`) — a conventional choice
for second-level data with autocorrelation decaying over a few seconds; no formal lag-order
selection procedure was run, and that is a stated limitation, not a tuned choice.

**AAPL:**

| Split | N train | N test | R²_in | R²_out | HAC(5) t-stat | HAC(5) p-value |
|---|---|---|---|---|---|---|
| Day-level (train d1–5, test d6–7) | 116,948 | 46,778 | 0.0000 | -0.0002 | -0.120 | 0.9043 |
| Walk-forward fold 1 (train d1–5, test d6) | 116,948 | 23,387 | 0.0000 | -0.0001 | -0.120 | 0.9043 |
| Walk-forward fold 2 (train d1–6, test d7) | 140,335 | 23,391 | 0.0000 | -0.0003 | 0.346 | 0.7291 |

**AMZN:**

| Split | N train | N test | R²_in | R²_out | HAC(5) t-stat | HAC(5) p-value |
|---|---|---|---|---|---|---|
| Day-level (train d1–5, test d6–7) | 116,948 | 46,778 | 0.0029 | 0.0031 | 4.511 | <0.0001 |
| Walk-forward fold 1 | 116,948 | 23,387 | 0.0029 | 0.0032 | 4.511 | <0.0001 |
| Walk-forward fold 2 | 140,335 | 23,391 | 0.0030 | 0.0027 | 5.289 | <0.0001 |

AAPL's predictive R² is statistically indistinguishable from zero (HAC p≈0.7–0.9) under the
corrected split — same conclusion as before, now measured correctly. AMZN's predictive R² is
small (0.3%) but statistically significant under HAC(5) (p<0.0001) given its large N; whether
0.3% R² is *economically* significant (net of any transaction cost / latency) is a separate
question not addressed here — flagged, not claimed as tradeable.

## Step 2F — Side-by-side comparison, no cherry-picking

**AAPL, raw OFI, 1s horizon, R²_out:**

| Methodology | R²_out |
|---|---|
| Original: within-day 70/30, incl. extended hours | -0.0018 |
| Day-level split (train d1–5 / test d6–7), regular hours | -0.0002 |
| Walk-forward fold 1 | -0.0001 |
| Walk-forward fold 2 | -0.0003 |

**The near-zero out-of-sample R² for AAPL survives the corrected methodology unchanged.**
This is a legitimate negative result, now measured without the within-day regime-shift
confound: raw Level-1 OFI at a 1-second horizon does not predict AAPL forward returns, in this
7-day sample, whether split within-day or by day. The original write-up's conclusion was
directionally right; the methodology it was reached with was not — the corrected version is
what should be cited going forward.

**AMZN differs:** original within-day R²_out was +0.0007 (also near zero, and the original
report's "AMZN shows a small but positive out-of-sample R²" language was descriptively
accurate for the flawed split too); the day-level/walk-forward R²_out (0.0027–0.0032) is
larger and HAC-significant. This did **not** flip from "no signal" to "signal" — both
methodologies show a small positive AMZN effect — but the corrected methodology gives a
cleaner, regime-safe estimate of its size and statistical significance. Given AMZN's unresolved
low contemporaneous R² (Step 2B), treat this predictive result with the same caution — and see
"Blocker 1" below, which supersedes the "unresolved" framing with an actual root cause.

**AMZN's 0.3% R² is statistically significant but economically negligible, and should not
stand unqualified.** At N≈117,000–163,000, HAC significance is nearly free — a t-stat of 4.5
on a coefficient this small reflects sample size, not tradeable edge. 0.3% of return variance
explained, before accounting for transaction costs, latency, or adverse selection on execution,
is not by itself evidence of a profitable signal. Statistical significance and economic
significance are answering different questions here; only the first was tested.

## Blocker 1 — AMZN's near-zero contemporaneous R² investigated as a suspected bug (2026-07-24)

Prompted by: OFI explaining ~0% of AMZN's contemporaneous price variation while allegedly
predicting future AMZN returns with HAC significance is internally contradictory — a signal
that can't explain concurrent moves shouldn't forecast them. Investigated as a suspected data
or reconstruction bug rather than accepted as a market finding, per instruction.

**(a) Stock-locate mapping.** Code read of `src/feed/itch_parser.cpp` and `src/main.cpp`: this
engine does **not** use `stock_locate` at all (explicitly skipped — see the file's own
byte-offset comment, "Offset 1-2 is stock_locate (we skip it)"). There is no Stock Directory
(`'R'`) message handling anywhere in the codebase. Filtering is instead done by matching the
literal ticker symbol embedded directly in `'A'`/`'F'` (Add Order) message bodies against
`filter_stock`. `'D'`/`'U'`/`'E'`/`'C'`/`'X'` messages carry no symbol field in real ITCH 5.0
and are **not filtered by ticker at all** in single-ticker mode — every such message in the
file is applied to the one open book, relying entirely on `orders_.find(order_ref)` silently
missing for refs that were never added. This is safe *only* if `order_ref` values are globally
unique across tickers, which is true for real Nasdaq ITCH data per spec but was unverifiable
here (no raw file). This was a real architectural finding, but not the actual bug — see below.

**(b) Price-level overflow.** Not pursued as a separate check. The root cause found in (c)
fully explains the observed symptoms without invoking the overflow/promotion path, and a
clean synthetic repro against current code (see below) showed correct spreads with no overflow
involvement. Reopen this check specifically if the overflow path is still suspect after data
regeneration.

**(c) Direct book sanity check — this is where the actual bug was found.** Checked
`quoted_spread` (computed by the engine as `curr.spread()`, i.e.
`(best_ask_price - best_bid_price) / 10000.0`, both `uint32_t`) across all 5 tickers,
regular-hours-only:

| Ticker | % of rows with spread > $1,000 | Median spread | Implied "crossed" amount (2³²/10000 − spread) |
|---|---|---|---|
| AAPL | 100.0% | $429,492 | $4.7296 |
| AMZN | 100.0% | $429,484 | $12.7296 |
| ETSY | 99.6% | $429,496 | $0.7296 |
| NFLX | 100.0% | $429,490 | $6.7296 |
| WDAY | 99.9% | $429,491 | $5.7296 |

**This affects all 5 tickers, essentially universally — not AMZN alone.** The "implied crossed
amount" column is `2³²/10000` minus the observed spread, i.e. what the true
`best_ask_price − best_bid_price` would have to be (as a negative number) to `uint32_t`-underflow
to the observed value. Every ticker's implied crossing shares the identical `.7296` fractional
part, differing only in a per-ticker integer dollar offset — a signature of a deterministic
byte-alignment bug, not real (and wildly implausible) multi-dollar market crossing on a
sub-$50–$1,900 stock.

**Root cause, confirmed:** `data/features_AAPL.csv` (file mtime 2026-05-04) and
`data/panel_AAPL.csv` (file mtime 2026-06-13) both predate commit `257956e` (2026-07-23,
"stock-truncation" fix from earlier this session), which widened the ITCH `'A'`/`'F'` stock
field from 4 to 8 bytes to match the real ITCH 5.0 spec. Every CSV in `data/` was generated by
the **pre-fix** parser, which read only 4 of the real message's 8 stock-symbol bytes — every
field after the stock symbol (i.e. `price`) was read 4 bytes out of position, for every
message, for every ticker, producing a corrupted, effectively-crossed reconstructed book.
Directly verified this is not a live bug: replaying a clean synthetic ITCH file through
**today's** engine (`build_audit/lob_engine`) produces sane spreads (0.05, 0.02, 0.02 dollars),
confirming current `order_book.cpp`/`feature_engine.cpp` are correct and the corruption is
confined to the stale files on disk.

**This means every number in this file — the original numbers AND this re-audit's "corrected"
numbers — was computed on corrupted data**, since both used the same stale CSVs/panels. The
day-level-split methodology fix (Steps 2C–2F) is still the right approach and should be
reapplied once fresh data exists; the R² values themselves need to be recomputed from
regenerated CSVs. See the critical notice at the top of this file.

**Why this plausibly explains the AAPL-vs-AMZN asymmetry without inventing a new mechanism:**
the corruption pattern is a fixed 4-byte read misalignment; its exact numeric effect on any
given field depends on the literal bytes straddling that misalignment, which differ by ticker
symbol and by each message's real share/price payload. A uniform mechanical bug producing
ticker-dependent corruption severity is exactly what's observed (AAPL retained a
literature-plausible contemporaneous R² despite corruption; AMZN's collapsed to ~0) — this is
recorded as the most parsimonious explanation consistent with the evidence, not as a
separately-confirmed sub-mechanism.

## Blocker 2 — extended hours: stated plainly

**The corrected re-run (Steps 2C–2F, and the Step 2B contemporaneous check) excluded extended
hours.** Every day-level, walk-forward, HAC, and time-of-day-normalization result above filters
each day's data to `sec_of_day` in `[34200, 57600]` (09:30–16:00 ET) before use — confirmed by
re-reading the audit scripts. Only the row explicitly labeled "ORIGINAL: within-day 70/30
(all hours)" in Step 2F used the full extended-hours day, and it is labeled as such precisely
so it isn't mistaken for a regular-session number. No further re-run is needed for this
blocker; this section exists only to state it plainly, as requested, rather than leave it
implicit in table headers.
