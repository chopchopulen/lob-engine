## Why this was re-audited

The original study used a chronological 70/30 train/test split **within a single trading
day**. Intraday microstructure is U-shaped — spreads, volume, volatility, and flow dynamics
differ sharply between open, midday, and close — so the final 30% of a day is a structurally
different regime from the first 70%. A near-zero out-of-sample R² measured that way can't
distinguish "the signal doesn't persist" from "the model was tested on different market
conditions than it trained on."

## Step 2A — Audit of the existing setup

1. **Session window: pre-market and post-market ARE included, confirmed.** `features_AAPL.csv`
   spans `ts` = 14,400.67s to 71,999.95s (04:00:00 to 19:59:59), not the regular 09:30–16:00
   session. Of 55,652 total rows, 19,468 (35%) are pre-market and 12,792 (23%) are
   post-market — **58% of the original study's data was extended-hours**, thin-liquidity
   trading that behaves nothing like the regular session. This makes the within-day split
   problem worse than the split alone would suggest, exactly as suspected.
2. **The regression is PREDICTIVE, not contemporaneous — confirmed by reading
   `scripts/analysis.py`.** `ofi_return_regression()` builds `fwd_col` via
   `mid_price.pct_change(shift).shift(-shift)`: OFI at row *t* is regressed against the return
   over `(t, t+h]`, a genuine forward return, not a same-interval contemporaneous one.
3. **OFI construction (`include/features/feature_engine.h`,
   `src/features/feature_engine.cpp:compute_ofi`):** Level-1 only for the main `ofi` column
   (separate `ofi_l1`/`ofi_l5`/`ofi_l10` columns exist for the depth study). Computed
   tick-by-tick on every book update — `e_bid` is `+shares` if best bid price rose, the size
   delta if price unchanged, `-prev_shares` if price fell (mirrored, sign-flipped, for the ask
   side) — and accumulated (`running_ofi_ +=`) across every book event within each 1-second
   window, then emitted and reset at the second boundary. This is the correct Cont, Kukanov &
   Stoikov (2014) construction, not a snapshot-difference approximation.
4. **Per-ticker, not pooled.** `ofi_return_regression()` takes one ticker's CSV at a time (the
   cross-asset function is separate and explicit about mixing tickers). 7 trading days are
   loaded per ticker via `data/panel_{TICKER}.csv` (2019-01-30, 03-27, 07-30, 08-30, 10-30,
   12-30, 2020-01-30) across 5 tickers (AAPL, AMZN, ETSY, NFLX, WDAY); the original Iteration 1
   study used only the single most recent day (`features_{TICKER}.csv`, identical to
   `features_{TICKER}_01302020.csv`) per ticker.

**RETRACTED, 2026-07-24, after "Blocker 1" below: "AAPL lands squarely in the literature's
range — the OFI implementation is sound" was the wrong conclusion, for a specific and
important reason, not just because the data turned out to be stale in general.**

AAPL's contemporaneous R² of 0.35–0.45 does **not** validate the OFI construction, and the
reason is worth stating precisely rather than just noting "the data was bad": `ofi` and
`mid_price` in this CSV were **both computed from the same corrupted book reconstruction** —
the same misaligned-read parser produced both columns, in the same process, from the same
(wrong) `best_bid_price`/`best_ask_price` values. Regressing one corrupted-but-internally-
consistent derived series against another corrupted-but-internally-consistent derived series
from the same source does not test whether the reconstruction is *correct* — it tests whether
`ofi` and `mid_price` move together, which they will if they're both functions of the same
(wrong) underlying state, corrupt or not. Landing in the literature's plausible range was
coincidence, not confirmation: two numbers derived from the same broken pipeline correlating
with each other, in a way that happened to resemble a published result, looks exactly like
success and is not.

**The lesson, stated explicitly so it doesn't get re-learned the hard way:** matching a
published result is not a correctness check on a data pipeline. It's a check that two
quantities correlate the way theory says they should — which corrupted-but-self-consistent
data can satisfy just as well as correct data, precisely because both quantities came from the
same corruption. The check that actually caught the bug was **inspecting the reconstructed
intermediate object directly** — printing `quoted_spread` and finding it was $429,492 on a
$321 stock (Blocker 1, Step (c) below). That check doesn't compare against a downstream
statistical target at all; it asks "is this intermediate value physically plausible," which a
regression R² landing in a plausible range cannot answer. Any future validation step for this
pipeline should default to inspecting intermediates (book state, spread, price levels)
directly, and treat a good R² as at best a weak, easily-fooled secondary signal — never as the
primary correctness evidence. This is now enforced automatically via `scripts/validate_book.py`
(see `PROJECT_STATUS.md`), which runs on every regeneration specifically because a human
checking "did the R² look reasonable" is exactly the check that failed here.

**AMZN's contemporaneous R² (0.0011) is consequently no longer a distinguished "open
question."** It doesn't need a separate explanation from AAPL's: both were computed on the
same class of corrupted data, and the corruption's effect on any given derived quantity depends
on the specific bytes involved (see "why this plausibly explains the AAPL-vs-AMZN asymmetry"
below) — a low R² and a coincidentally-plausible R² are both explained by the same root cause,
not two different phenomena requiring two different stories.

**Conclusion: implementation validated via AAPL. Proceeding to the corrected split, per the
instructed branch ("if high, the implementation is likely sound").**

## Step 2C/2D — Day-level split + walk-forward, HAC(5) standard errors

Regular-hours-only (09:30–16:00), 1-second predictive horizon, `data/panel_{TICKER}.csv`.
Fold count is **honest and small**: 7 days total gives one primary train/test split (5 days
train / 2 days test) and only 2 walk-forward folds (expanding window). This is a real
limitation — 7 days is not enough to characterize a stable out-of-sample distribution, only
enough to check whether the near-zero result survives a coarser, regime-safe split.
Newey-West/HAC standard errors use 5 lags (`cov_kwds={'maxlags': 5}`) — a conventional choice
for second-level data with autocorrelation decaying over a few seconds; no formal lag-order
selection procedure was run, and that is a stated limitation, not a tuned choice.

## Blocker 1 — AMZN's near-zero contemporaneous R² investigated as a suspected bug (2026-07-24)

Prompted by: OFI explaining ~0% of AMZN's contemporaneous price variation while allegedly
predicting future AMZN returns with HAC significance is internally contradictory — a signal
that can't explain concurrent moves shouldn't forecast them. Investigated as a suspected data
or reconstruction bug rather than accepted as a market finding, per instruction.

**(a) Stock-locate mapping.** Code read of `src/feed/itch_parser.cpp` and `src/main.cpp`: this
engine does **not** use `stock_locate` at all (explicitly skipped — see the file's own
byte-offset comment, "Offset 1-2 is stock_locate (we skip it)"). There is no Stock Directory
(`'R'`) message handling anywhere in the codebase. Filtering is instead done by matching the
literal ticker symbol embedded directly in `'A'`/`'F'` (Add Order) message bodies against
`filter_stock`. `'D'`/`'U'`/`'E'`/`'C'`/`'X'` messages carry no symbol field in real ITCH 5.0
and are **not filtered by ticker at all** in single-ticker mode — every such message in the
file is applied to the one open book, relying entirely on `orders_.find(order_ref)` silently
missing for refs that were never added. This is safe *only* if `order_ref` values are globally
unique across tickers, which is true for real Nasdaq ITCH data per spec but was unverifiable
here (no raw file). This was a real architectural finding, but not the actual bug — see below.

**(b) Price-level overflow.** Not pursued as a separate check. The root cause found in (c)
fully explains the observed symptoms without invoking the overflow/promotion path, and a
clean synthetic repro against current code (see below) showed correct spreads with no overflow
involvement. Reopen this check specifically if the overflow path is still suspect after data
regeneration.

**(c) Direct book sanity check — this is where the actual bug was found.** Checked
`quoted_spread` (computed by the engine as `curr.spread()`, i.e.
`(best_ask_price - best_bid_price) / 10000.0`, both `uint32_t`) across all 5 tickers,
regular-hours-only:

| Ticker | % of rows with spread > $1,000 | Median spread | Implied "crossed" amount (2³²/10000 − spread) |
|---|---|---|---|
| AAPL | 100.0% | $429,492 | $4.7296 |
| AMZN | 100.0% | $429,484 | $12.7296 |
| ETSY | 99.6% | $429,496 | $0.7296 |
| NFLX | 100.0% | $429,490 | $6.7296 |
| WDAY | 99.9% | $429,491 | $5.7296 |

**This affects all 5 tickers, essentially universally — not AMZN alone.** The "implied crossed
amount" column is `2³²/10000` minus the observed spread, i.e. what the true
`best_ask_price − best_bid_price` would have to be (as a negative number) to `uint32_t`-underflow
to the observed value. Every ticker's implied crossing shares the identical `.7296` fractional
part, differing only in a per-ticker integer dollar offset — a signature of a deterministic
byte-alignment bug, not real (and wildly implausible) multi-dollar market crossing on a
sub-$50–$1,900 stock.

**Root cause — CONFIRMED 2026-07-24 by direct reproduction, correcting the retraction above.**
An earlier version of this section claimed the pre-item-4 parser "read only 4 of the real
message's 8 stock-symbol bytes — every field after the stock symbol (i.e. `price`) was read 4
bytes out of position." That specific claim was checked against the commit diff and found
wrong (see the "golden fixture" investigation, `PROJECT_STATUS.md` Task 5) and briefly
retracted with no confirmed replacement. It has now been replaced with a mechanism confirmed by
directly running the actual pre-fix binary against real data, not just reading diffs.

**Reproduction:** checked out commit `257956e^` (`078d196`, the parser immediately before the
item-4/1/2 fixes) in an isolated `git worktree`, built it unmodified, and ran it against the
same real Nasdaq BX ITCH sample used throughout this investigation
(`20190730.BX_ITCH_50`, downloaded from `emi.nasdaq.com`). Result: the exact corruption
signature reproduces.

| Ticker | Rows with `\|spread\| > $1,000` | Total rows | % corrupted |
|---|---|---|---|
| AAPL | 699 | 28,215 | 2.5% |
| MSFT | 26,571 | 28,831 | **92.2%** |

Every corrupted row's spread is exactly `$429,497` — the same `uint32_t`-underflow signature
identified earlier (`2^32/10000 ≈ $429,496.73`). This is the pre-fix parser reproducing the
exact bug on real data, confirmed, not inferred.

**Mechanism, read directly from the pre-fix code (`itch_parser.cpp` and `main.cpp` at
`257956e^`):** `'A'`/`'F'` (Add Order) messages *were* correctly filtered by ticker even before
item 4 — the `filter_stock` comparison used the untruncated 8-byte buffer, confirming the
earlier retraction was right that item 4 itself wasn't the cause. But `'D'`/`'U'`/`'E'`/`'C'`/
`'X'` messages carry no ticker symbol in real ITCH 5.0, and the pre-fix parser applied **no
filtering of any kind** to them — every such message in the entire file, for every ticker, was
delivered to whichever single `OrderBook` was open. `main.cpp`'s single-ticker callbacks
(`cb.on_delete`, `cb.on_replace`, `cb.on_execute`) called `book.delete_order`/`replace_order`/
`execute_order` **unconditionally** on every delivered message, with the only protection being
`OrderBook::orders_.find(order_ref)` silently missing for refs that ticker's book never added.
This session's earlier "Blocker 1(a)" investigation identified this exact architectural gap and
assumed it was safe in practice, reasoning that real Nasdaq order references are unique across
the whole feed per spec. **That assumption does not hold at the observed corruption rate**: on
real BX data, MSFT's book was corrupted in 92% of reconstructed rows, which requires far more
`order_ref` collisions between MSFT and other tickers' messages than a genuinely
globally-unique numbering scheme should produce. The exact reason `order_ref` collisions occur
this frequently on BX (venue-specific numbering, ID reuse, or something else) is not further
characterized here — the mechanism that caused the corruption (unconditional cross-ticker
message delivery) is confirmed; the deeper reason `order_ref` isn't the safety net it was
assumed to be is not.

**This is not item 4, and item 4 never touched it.** `257956e`'s diff to `itch_parser.cpp` only
changed the `'A'`/`'F'` `strncpy` width and added `'C'`/`'X'` message handling — it did not add
ticker filtering to `'D'`/`'U'`/`'E'`/`'C'`/`'X'`. That filtering did not exist anywhere in this
repository's history until this session's **Task 2** (`stock_locate`-based filtering across
every message type, commit `3253443`) — meaning every `data/` CSV generated by any engine
version before that commit, regardless of whether item 4 had landed, carried this exact
vulnerability. Confirmed directly: replaying the same real BX file through **today's** code
(post-Task-2) produces clean, sane spreads (0.03, 0.02) with zero corrupted rows — the same
real-data test, before and after the actual fix, both run this session.

**What this changes from the prior retraction:** the mechanism is now confirmed, not unknown.
The AAPL-vs-ticker severity asymmetry is real and now has a concrete (if not fully
characterized) explanation: corruption severity tracks how often a given ticker's `order_ref`s
collide with the flood of unfiltered foreign-ticker `'D'`/`'U'`/`'E'`/`'C'`/`'X'` messages,
which plausibly varies by ticker based on message volume and `order_ref` proximity — this is a
weaker, more honest claim than the original retracted mechanism, not a restatement of it. The
"matching literature isn't a correctness check" lesson is unaffected either way — it never
depended on which bug caused the corruption.

### Proposed filter (NOT YET APPLIED — awaiting approval of thresholds)

Even though this date's regular-session data is already fully clean, a documented, permanent
filter is proposed as defensive infrastructure for the eventual multi-date panel, where a
messier date or a thinner ticker could produce an intra-session degenerate quote that this
date happens not to exhibit. Proposed rule, to live as a documented step in the data-loading
path (e.g. `scripts/analysis.py`'s `load_features()`, alongside `verify_provenance()`), applied
identically to every ticker with no per-name exceptions:
